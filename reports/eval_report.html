Haiku 5.5 与 DeepSeek 数据处理评测

用 pi 在四种出题方式下对比 Claude Haiku 5.5 与 DeepSeek V4.1-Flash-1017（下文分别简称 Haiku、DeepSeek）的数据处理与分析能力。共两套题库：v1 用于逐步提高出题难度，v2 是更接近真实工作的高难度题库。每套题库分 10 个难度等级、每级 20 题，累计超过 4,000 次模型运行。

结论

  • 正确率：两套题库得出两种结论，但都很接近。v1 无提示题库上，Haiku 3 轮均值 199.0/200，DeepSeek 195.7/200，Haiku 小幅领先且有统计意义（+1.67 pp，p = 0.039）。v2 高难度题库上，两者 3 轮均值都是 197.7/200，正确率差为 0，95% 置信区间 [−1.33, +1.33]。
  • v1 的差距来自“规范没写到时怎么判断”，而不是计算能力。DeepSeek 在 v1 的 13 次失败中有 11 次出在 A/B 实验：它多数时候发现了同时分在两组的用户，却以“规范没逐字写明”为由选择不处理（第 05 节）。v2 把实验题的统计口径都写全后，这一差距没有再出现。
  • 单纯提高难度拉不开差距。v1 写明口径时两者都是 200/200。v2 把题目换成对账、实体合并、变更日志回放、MRR 瀑布、多触点归因、根因分解等更难的任务，两者仍都在 98.8%。区分能力的，是需要自己判断的模糊地带。
  • 两个模型的失误风格不同。v2 中，Haiku 的 7 次失误有 5 次出在最简单的 L1–L2，主要是把 README 的通用规范套用到了不该用的计数题上，而且它常在说明里写出了另一种口径下的正确数。DeepSeek 的 7 次失误都在 L4 及以后，主要是读错定义（3 次）和把答案写进了子目录（2 次）。
  • 效率随任务复杂度分化。简单、口径明确的任务 DeepSeek 更快更便宜：v1 有提示时快 36%、便宜 29%。多步复杂任务 Haiku 更快更省：v2 平均每题 46.0s 对 54.5s，工具调用 6.6 次对 9.0 次，费用低约 7%。DeepSeek 的中位耗时略低，但慢题更多，v2 的 P90 耗时为 127s 对 86s。
  • 选型建议。口径清楚、以简单查询为主、对延迟和成本敏感的批量任务，选 DeepSeek。多步骤的复杂分析，或者规范不完整、需要模型自己补全口径的脏数据，选 Haiku。无论用哪个，都应该把关键的处理规则写进提示词。

数据集与陷阱

第 2–4 轮使用同一套电商数据：订单 2.5 万条、订单明细 4.9 万条、行为事件 5.4 万条，另有客户、商品、汇率、每日指标、旧系统导出、A/B 实验、员工、客服工单。生成时先得到干净真值，再按规则“弄脏”写入文件。标准答案只从真值计算，不依赖任何清洗代码。为防止题面规则与真值不一致，另写了一个只读脏文件的独立清洗器做核对，16 项核心字段与真值完全一致。

判分方式

每道题在独立的工作目录中运行，模型自己写 Python 代码，最后把答案写入 answer.json，或按要求输出 CSV。数值题按题目要求的小数位允许 1 个末位单位的舍入差；整数题和字符串题要求完全一致；CSV 题先核对列名和行数，再逐格比对。判分器做过反向测试，CSV 中篡改 0.05 即被判错。

第 3、4 轮的 README 是一份普通的数据字典：只写字段含义、字段约束（如“主键”“正整数”“非负”“每个用户只属于一个组”）、业务口径（时区、GMV 公式、汇率规则）和 5 条通用分析规范。它不提示哪张表、哪个字段有什么问题。保留通用规范是有意的取舍：如果完全不给处理口径，同一个问题会有多种合理做法，评测就成了猜出题人的口径。

05

DeepSeek 在 v1 A/B 题上失误的原因

A/B 实验文件里有 30 个用户同时出现在 A、B 两组。数据字典写着“每个用户只属于一个组”，通用规范写着“违反字段定义的值视为无效，只把该字段当作缺失”。按这两条，这些用户的组别无效，应从分组分析中整体剔除，这也是 A/B 实验分析的常规做法。

结论先说：DeepSeek 在这里的问题不是不会算，也基本不是没发现。它多数时候发现了冲突，却选择“不处理”，而且这个选择在多次运行之间来回摇摆。下面是逐次分析事件日志得到的证据。

证据一：错误答案与“不处理”口径逐位一致

12 道 A/B 相关题中，有 7 道的答案会随处理方式改变（其余题不受影响，或差异小于判分容差）。对这 7 道题按三种口径分别计算，DeepSeek 的 11 次错误答案全部与“不处理”一致，没有一次是“保留首条”。

证据三：写明规则时，它全部做对

第 2 轮的 README 明确写了“同时出现在 A 组和 B 组的用户为污染样本，分析时剔除其全部记录”。这 7 道题 DeepSeek 全部答对。所以它有能力执行这个处理，差别只出在规则没有逐字写明的时候。

它为什么选择不处理

在 8 次“发现了冲突却不处理”的运行里，DeepSeek 的思考过程反复出现以下理由（同一次运行可能出现多条）：

理由出现次数
这是跨行或主键层面的约束，不属于“某个字段的值违反定义”，所以通用规范管不到8 / 8

DeepSeek（第 1 轮 #110）：“user_id 重复不是值本身非法，而是跨行约束违反。规范未给出处理跨行唯一性冲突的方法。并且‘不要因为看起来异常而剔除’支持保留。”

Haiku（第 1 轮 #107）：“这 30 个用户同时出现在 A 组和 B 组，违反‘每个用户只属于一个组’的字段定义。无法确定他们的分组，所以把 group 视为缺失，这些记录不参与计算。我用排除后的数据计算，并给出保留它们时的结果作对照。”

根因归纳

  • 字面、最小干预地解读规范。DeepSeek 把明文写出的去重规则当成完整清单，又把“违反字段定义”限定为单个字段值本身非法。规范没有逐字覆盖的情况，它默认不处理。
  • 把一条规范用错了地方。“不要因看起来异常而剔除”本来是针对数值异常（比如单价误录 10 倍）写的，它被拿来为保留结构性冲突的数据辩护。
  • 决策在多次运行之间摇摆。同一道题会出现对、错、对交替（#109 为 ✗ ✓ ✗）。8 次里有 5 次已经算出了正确值仍然放弃，说明两种解释在它的推理里势均力敌，最后取哪一种近乎随机。
  • 偶有推理失误和少量漏检。第 2 轮 #120 中，它注意到转化用户里的 user_id 没有重复，就断定冲突用户“不影响本题”。实际上剔除这些用户后，有 5 个转化用户会被排除，结果确实会变。另有 3 次完全没有检查跨组情况。

Haiku 面对同一份 README，把“每个用户只属于一个组”直接当作字段定义的一部分。冲突意味着组别无效，组别无效就不参与分组。这与 A/B 实验的常规做法一致，它 21 次都这样处理，说明里也常常附上保留这些用户时的对照结果。

这部分差距有多少要算在出题上

README 确实没有逐字写“跨组用户整体剔除”。DeepSeek 认为这是跨行约束、不是字段值，这个反对意见有一定道理。如果把“不处理”也算作可接受答案，DeepSeek 3 轮平均为 199.3/200，Haiku 为 199.0/200，两者持平。

所以对第 4 轮更准确的描述是：当规范没有逐字覆盖某种数据问题时，Haiku 倾向按领域惯例补全规范并说明理由，DeepSeek 倾向字面执行、最小干预，而且判断不稳定。对数据分析工作来说，前者通常更符合预期；但这体现的是判断风格的差异，不是计算能力的差距。

使用建议：用 DeepSeek 做数据分析时，把关键的处理规则逐条写进提示词，第 2 轮的结果说明写明后它能稳定执行。也可以明确要求它“遇到数据冲突时按领域惯例处理，并同时给出不处理时的对照结果”。

07

v2：更难、更接近真实工作的题库

v1 去掉提示后，差距集中在 A/B 实验这一类，整体仍接近满分。v2 换了一套全新的数据和题目，题型聚焦数据工程与分析中真正费力的环节。v2 沿用 v1 无提示版的做法：README 是数据字典，只写字段约束、业务规则和通用规范，不提示具体问题。不同的是，v2 把夏令时、订单多次导出、文件格式这类必须约定的规则写清楚，统计题的公式也全部给出。所有任务都在 bubblewrap 沙箱中运行，两个模型各跑 3 轮。

数据与题型

失误分析

修正题目缺陷后（第 08 节），每个模型 3 轮共剩 7 次失误，分布在不同的题目上，没有哪道题被某个模型 3 轮全错。

题号等级Haiku 第 1–3 轮DeepSeek 第 1–3 轮原因类型
  • Haiku 想得太多。7 次失误中有 4 次是把 README 的通用规范用在了不该用的地方：题目要“全部订单”，它按“有效订单”只数了 completed；题目问“出现在多个文件中的订单”，它先去重，结果自然是 0；题目问“超出合理范围的读数”，它先把 999.9 当作缺失值，于是答 0。这几次它通常在说明里写出了另一种口径下的正确数，只是最后选错了。
  • DeepSeek 读得不够细。它 3 次把“入库之后、出库之前库存为 0”理解成“日终库存为 0”；2 次先 cd 进子目录，再用相对路径写答案，答案本身正确，却没有写到要求的当前目录。
  • v1 的 A/B 差距没有重现。v2 的实验题把统计口径写全了，不需要模型自己决定“发现数据冲突后怎么处理”。这一点也印证了第 05 节的判断：v1 的差距来自规范未覆盖时的判断风格，而不是统计能力。
  • 复杂任务上 Haiku 更高效。L3–L7、L9、L10 都是 Haiku 更快，L10 平均 71.9s 对 98.5s。DeepSeek 只在 L1 和 L8 这类直接计算的题上更快。DeepSeek 平均多调用 2.4 次工具，输入 token 多 52%，所以虽然它的单价更低，每千题费用反而高约 8%。
08

行为观察与评测本身的修正

遇到歧义时会多算几种口径

第 2 轮 README 有一处没写清：revenue 为负的那一行，dau 是否仍然有效。两个模型都察觉到了歧义，从事件日志看，它们都把“整行剔除”和“只剔除 revenue”各算了一遍，最后都选了整行剔除。这类主动核对是两个模型的共同优点，但也说明口径不清时，“答错”可能只是选了另一种合理解释。

写出到工作目录之外

提示词要求只在当前工作目录内读写，但两个模型都有越界，Haiku 更频繁。它多数时候把脚本写成 /tmp/calc.py，有一次把 answer.json 写到了上两级目录。

3 次重复是并行运行的，多个任务会同时读写同一个 /tmp/calc.py，存在互相覆盖的风险。核查结果：Haiku 用到该文件的 60 个任务全部正确，没有任何一道失败题与文件覆盖有关，上面的结论不受影响。模型留在 /tmp 的 45 个文件已按事件日志逐一确认后删除。此后运行器改为默认在 bubblewrap 沙箱中执行：每题有独立的 /tmp，只有题目目录可写，家目录中的其他内容不可见。

v2 的任务更重，Haiku 写 /tmp 的比例升到 46.5%。这些写入都只落在各自沙箱的临时层，任务之间不会互相覆盖，宿主机上也没有残留。如果没有沙箱，3 轮并行时文件互相覆盖的风险会高得多。

v2 运行中的基础设施事故

v2 第一次运行时，评测账号的调用额度中途耗尽，之后每次调用都返回 403（insufficient_user_quota）。当时 Haiku 的任务全部排在 DeepSeek 之后，所以 600 次一题都没跑到；运行器又把这类接口错误记成了“模型没写答案、答错”，既没重试也没停下来。处理过程如下：

  • 修复判定。运行器改为：只要事件日志里出现过接口报错，就记为基础设施失败并自动重试，不算模型答错。
  • 修复已有记录。按事件日志重新判定旧记录，只保留未受影响的记录。中途碰到报错、但已经写过答案的 7 条记录也一并重跑。
  • 防止再次发生。两个模型的任务改为交替排队；连续 8 个任务因额度不足失败时自动停止派发。
  • 补跑结果。额度恢复后补跑了 959 个任务，没有再出现接口失败。报告中的 v2 数据全部来自有效运行。

评测过程中发现并修正的题目缺陷

每次出现失败，都先判断是模型的错还是题目的错。下面这些属于题目的错。每项修正都对两个模型同时生效，受影响的题两个模型都重跑了。

09

局限

  • 只覆盖了一种配置。两个模型都用默认思考强度、同一个调用渠道；没有测试关闭或提高思考强度的效果。
  • 只有一个数据领域，题面全是中文。结论来自电商场景下有唯一标准答案的计算题，不代表开放式分析、写报告或可视化能力。
  • v1 的结论依赖一个判分口径。v1 第 4 轮的差距主要来自 A/B 题的“整体剔除”口径。这个口径由 README 的两条规则推出，也符合实验分析惯例，但 README 没有逐字写明；如果同时接受“不处理”，两者持平（第 05 节）。
  • 差距小，样本有限。两套题库的正确率差都在 2 个百分点以内。v1 的差距由 7 道 A/B 题决定，v2 打平；换一套题目权重，总分差可能变化。
  • 题目有唯一标准答案。为了自动判分，每道题都有明确的定义和唯一答案。这测的是“在给定口径下把数据处理对”的能力，不涵盖开放式探索、提出好问题、写分析报告。
  • v1 运行时没有系统层面的沙箱。v1 四轮中，越界写文件只靠提示词约束（第 08 节）；v2 全部在 bubblewrap 沙箱中运行。沙箱里网络仍是开放的，pi 的模型配置（含 API key）在沙箱内可读。
  • 出题方与被测模型同属一家。题目和判分由 Claude（Opus 5.5）设计。为减少偏向：标准答案从生成数据时的真值计算；两个模型使用完全相同的提示词；每道失败题都核对过事件日志，题目缺陷修正后两个模型一起重跑。即便如此，题目风格可能更接近 Claude 系模型的习惯，这一点无法完全排除。
